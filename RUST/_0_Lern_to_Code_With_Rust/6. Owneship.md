# Memory management

**memory**
- is an actual piece of hardware (that is responsible for storing the information that your program use )
- is use for temporary , dynamic data that your programs need as thay are riunning
- is limited, so:
	- the program  should clean up the memory **deallocation**
	- **allocation** a program requests memory



## Manual memory management
C, C++ 
	- the programmers are responsible for allocating (requesting memory) and deallocation  (giving memory back to the computer)
	- programmers make mistakes:
		- forgetting to deallocate
		- deallocating memory that has already been deallocated

## Garbage Collector GC
Java, Python Ruby, Go:  **garbage collector**
	- the GC looks for data that is no longer in use and deallocates it
	- the GC itself occupies memory and can run at disadvantagous times


## Ownershipt
Rust - OWNERSHIP:
	- it is a set of rules ho how Rust manages your computer's memory
	- the Rust compiler does not compile the program if an ownershipt rule is violated
	- Best of all worlds: the speed of a language like C but with less room for error

# Ownership
#rust/ownership 
**Ownership** 
- is a Rust compiler feature
- has no impact on the actual program when it runs
- is a set of rules that the compiler checks for to ensure that the final program is free of memory errors



>[!info]  ownership's rule
> 
> - the owner is who/what is responsible for cleaning up a piece of data when it is no longer in use
> - every value in a Rust program has one owner
> - the owner can change over the course of the program, but there is only 1 owner for a value at a time
> - the owner is usually a name
> 	- a variable can be an owner
> 	- a parameter can be an owner
> - Owner ship also extends to composite types that own their elements
> 	- a tuple and array own their values

==ownership==
- the purpose of ownership is to assign responsibility for deallocating memory (primarily heap memory)
- ownership is a compiler feature for reducing duplicate heap data and cleaning up heap data that is no longer needed




# Stack and the Heap
#rust/heap #rust/stack 

- the **stack** and the **heap** are two different pars/regions of the computer's memory
- the **stack** and **heap** read and write data in different ways that offer advantages and disadvantages

>[!danger] STACK
> - stores values in the sequential order it receives them
> - is LIFO (the last item added is the first one removed)
> - **pushing onto the stack** - means adding data
> - **popping off the stack** - means removing data
> - is fast
> 
> 
> - all stack data has a fixed, consistent size that is known at compile time
> - data types like integers, floating-points, Booleans, characters, and arrays have a fixed size. Rust stores them on the stack at runtime
> - the pieces of data on the stack will not grow or shrink in size as the program runs
> 
> 
:::



>[!danger] HEAP
> - the heap is large area of storage space. Think of it like a warehouse
> - the heap is for data whose size is not known at compule time (user input, a file's contents, ...)
> - is slower then stack
> - when the Rust program needs dynamic space, it requests it from the heap. A program called the **memory allocator** finds an emptu spot that is large enough to store the data
> 	- MEMORY AALLOCATOR returns a **reference**, which is an address
> 	- the reference point to the memory address of the data
> 	- a reference can be store in a variabe in a Rust program
> 	- references have a fixed size, so Rust store them **on the stack**

# Scope and Ownership

Every Rust value has an owner, and that includes both values on the stack and values on  the heap.

```rust
fn main(){
	let age: i32 = 33;

	{
		let isGood = true;
		//isGood exists here
	} // isGood goes out of the nested scope


	// age variable exists here
} //age variable goes out of scope here
```

- `age` is the owner of the value `33`
- the owner is responsible for cleaning up the data
- the owner knows to clean up the data when the variable goes out of scope (when the block ends)

# The Copy Trait
#rust/copy 

**a trait is like a contract that a type promises to uphold**

>[!important] Copy Trait
>- It mandates that a type can be copied, which means that a fill duplicate can be created from it
>- Implement this trait by default - primitive data types:
>	- integer, floats
>	- Booleans
>	- character
>	- ....

```rust
fn main(){

	let time = 2025 ;
	let year = time ; // year will have a copy of time

}
```


## The copy trait with references
**reference** 
- it is an address but it's still a type
- it implement the Copy Trait:
	- if we have a variable storing a reference and
	- we assign that to another variable
	- Rust will CREATE a COPY of the reference

```rust
fn main() {
    
    let abc: &str = "abcde" ;
    let new_ref: &str = abc;
    println!("{abc}") ; //abcde
    println!("{new_ref}") ; // abcde
    
}
```

# Moves and Ownership

>[!info] M O V E
>a move is the transfer of ownership frome one owner to another

```rust
fn main() {
    let person: String = String::from("Boris") ;
    
    // Rust copies previous stack entry (the reference to the heap data, length , capacity)
    // on the heap is still one piece of data, byt now we have two references to it on the stack
    // When we assign "person" to "genius", Rust moves ownership from the "person" variable
    // to the "genius" variable
    // "genius" becomes the owner
    // "person becomes invalid"
    let genius: String = person ; // String does not implement the Copy trait
    println!("{genius}") ; //Boris
    // println!("{person}") ; // error
    
} // Rust uses `drop` function to clean up the memory
```

# References and Borrowing (`&`)
#rust/borrowing 

**a reference** allows the program to use a value without moving ownership

>[!important] BORROWING
>- means using something without taking ownership of it
>- means to create a reference to some value without taking ownership of it
>- `&` borrow operator

```rust

fn main() {
    let my_stack_value: i32 = 2;
    let my_int_reference: &i32 = &my_stack_value ;
    println!("{my_stack_value}") ;          // 2
    // W Rustie formatowanie przez {} (czy {:#?}) 
    // dla referencji domyślnie wypisuje zawartość (czyli to, na co wskazujesz), 
    //a nie adres w pamięci. 
    println!("{my_int_reference}") ;        // 2
    println!("{:p}", my_int_reference); // 0x7fff8945c134
    
    let my_heap: String = String::from("Toyota") ;
    let my_heap_reference: &String = &my_heap ;
    println!("{my_heap}") ;                 // Toyota
     // W Rustie formatowanie przez {} (czy {:#?}) 
    // dla referencji domyślnie wypisuje zawartość (czyli to, na co wskazujesz), 
    //a nie adres w pamięci. 
    println!("{my_heap_reference}")      ;   // Toyota
    println!("{:p}", my_heap_reference) ; //0x7fff8945c134
}
```

#rust/dereference

# Ownership and Function Parameters

The same ownership rules are going to apply to functions and their parameters!!!
A parameter is like a variable.
- Data type that implement Copy trait -> Rust will create a **copy** of the data for a function's argument
- heap data -> Rust will  **move** ownership to the function parameter

```rust
fn main() {
    let apples: i32 = 6;
    print_val(apples) ; // copy and print Val=6
    println!("apples {apples}") ; // apples
    
    
    let text: String = String::from("Some text") ;
    print_str(text) ; //Text = Some text
    // println!("{text}") ; error String data was moved to function
}


fn print_val(val: i32){
    println!("Val = {val}") ;
}

fn print_str(val_str: String){
    println!("Text = {val_str}") ;
}

```

# Mutable parameters

- we can transfer ownership from a mutable variable to a immutable variable
- we can transfer ownership from a immutable variable to a mutable variable

```rust
fn main() {
   let abc = String::from("xyz") ;
   add_text(abc) ; //xyz new text

}

fn add_text(mut text: String){
    text.push_str(" new text");
    println!("{text}") ;
}

```
